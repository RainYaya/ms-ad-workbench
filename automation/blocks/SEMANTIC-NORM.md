# SEMANTIC-NORM —— 语义归一层说明

更新: 2026-10-24 · 实现在 `tools/build_blocks.py` 的 `event_pattern()` 一族函数

## 为什么需要

450 本手顺是很多人分工写的，同一个业务动作存在多种书写：
`「検索」押下` / `検索` / `検索ボタン押下`、`初期値` 写不写、`画面HC` vs `（目視確認）`、
`－` vs `ー` vs `-`、`不備内容入力画面-更新` vs `不備内容入力画面 ー更新`。

机械字符串比对会把同一个动作判成不同（例：AZ-150-13-004 与 AZ-160-01-004 的第一步
业务上完全相同，仅书写不同，旧匹配配不上）。归一层在**比对之前**把书写变体折叠成同一个
规范键，业务不同的动作永远不合并。

## 归一规则（每条都有实例依据）

| 规则 | 例 | 依据 |
|---|---|---|
| 画面名：全角横线/长音符统一为 `-`、去空格、去尾缀`画面` | `不備一覧画面`→`不備一覧` | 38-001 vs 160-01-004 |
| 按钮名：去 `「」` 引号、去尾缀 `押下`/`ボタン` | `「検索」押下`→`検索` | 150-13-004 vs 160-01-004 |
| click 的 dataClass 差异忽略 | literal/none→none | 按钮书写差 |
| 遷移確認的 dataClass：literal/none/bundle 视为等价 | 初期値写不写 | 150-13-004 行15 |
| AZ/AY 姊妹画面等价 | 申込書品質管理メニュー≡異例取扱管理メニュー | 同一 SUT 两子系统 |
| 全部 *バッチ処理/*処理/*ファイル 画面 → 通配类 BATCH | 六个集計batch同构 | 150-07-001 六连batch |
| BATCH 类内 確認(操作結果/テーブル/ログ) 的 dataClass 统一 | — | 150 系书写差 |
| 外部認証後的门户画面 target 等价 | 代理店MS/AD | 角色参数非业务差 |
| 登录步标签等价 | ログイン画面/ダミーログイン画面/メニュー画面/ログイン | 200-01/200-04/AY-100-04 |

## 永不合并的（业务边界）

- `権限エラー` ≠ `システムエラー`（不同错误类型，各自有积木）
- MS 画面 ≠ 代理店画面（角色不同，UI 不同，只归名字变体）
- ボタン名永远进入匹配键（検索≠更新≠登録）

## 全覆盖兜底（2026-10-24 第三轮）

前两轮之后仍有 2,925 个未カバー事件。逐段分析发现 99 种段跨书重复（要再申請、一時中断、
承認、担当者検索、訂正内容確認書、代理店照会、営業連携、完了登録……全是高频按钮组合，
只是不满足自动挖掘的"op开头ast结尾"形状规则）。用户的判断成立：这个系统就是那几十个
操作的排列组合。

三层兜底机制（`build_blocks.py`）：
1. **auto 挖掘门槛 3→2 本书**：跨 2 本的重复段即可立块（归一化后同签名＝同业务动作）。
2. **BLK-SHR-\***：仍不满足挖掘形状的跨书重复段（纯确认段、跨画面段）立共享草稿块，68 块。
3. **BLK-SGL-\***：每本书剩余的独有段立单例块（终扫强制），133 块。任何一行都不允许裸露。

## 第四轮：块分类与去重（2026-10-24 下午）

用户指出 294 块仍太碎、"明明一样的还立新块"。核实属实：

1. **跨书重复 bug**：终扫生成单例块时未做签名去重，8 个 `BLK-SGL-*` 签名完全相同。已修：
   同签名段复用同一块并自动升级为 shared。
2. **块分类（kind 字段）**：每个块标记为
   - `family`（158）：多步业务流，需人审，执行单位
   - `primitive-nav`（20）：点按钮→跳转，纯导航
   - `primitive-act`（32）：单动作（点按钮触发处理）
   - `primitive-fill`（13）：填表
   - `primitive-verify`（29）：画面/工件确认
   原语是参数化的原子（这个 SUT 的全部零件就这 94 个位置），family 是人审的复用流。
3. **family 骨架 100 种**：其中「检索三兄弟」（各項目→検索→表示，105/96/40/36 本）属
   同一业务动作仅画面不同——参数化合并候选；但「更新/確認済/完了登録」同骨架不同按钮
   **业务后果不同，禁止机器盲并**。参数化逐族人审后执行，不自动。
