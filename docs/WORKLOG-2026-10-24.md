## 三、试了哪些、哪些不行、犯了哪些错

### 我犯的错（按疼的程度排序）

1. **没读手顺书就开方案**。初版评估问了一堆"跑几轮、DB谁管"，被用户一针见血：
   "你问的这些问题，感觉就是没有看那个手顺才问出来的。" 对。手顺每行都是
   操作+確認+証跡，写得极规整，读了就不该问那些。
2. **在错误的机器上验证**。在家用机起 mock 测 node runner，用户叫停。目标环境是公司机。
3. **heredoc 传长脚本三次被截断**，浪费了好几轮。教训：长内容用 Write 工具或分小段打补丁。
4. **初版归一层引入后，组合器让 auto 草稿挤掉了 curated 人审块**（009 从 10 块全
   curated 变成 13 块全 auto）。根因：curated 的 `_pattern` 构建绕过了归一化函数。
   修复后 curated 优先且同走归一。
5. **终扫生成单例块没做跨书去重**：8 个 BLK-SGL 签名一模一样还各占一坑——
   用户说的"明明一样的还立新的"。已修，同签名自动复用。
6. **假阳性 verified**：AZ-111-02-004 曾显示"検証済 1"，真相是它只有 2 块积木
   （恰好都 verified）而剩余行未カバー不计入判定。全覆盖兜底补上第 3 块后
   诚实降回 coded。**这是我上一轮口头解释时说错、事后查 git 才纠正的**
   （我当时甩锅给 AGENT-SELECT 归类变化，不成立）。教训：解释数字变化必须查数据。
7. **PowerShell 那条路上的历史坑**（上家 AI 踩的，记录在此防重蹈）：Edge 155 默认
   profile 开不了 CDP 端口；popup 竞态；here-string 注参三层引号。

### 试过不行的方案

- **机械归一化 alone**：只做字符串归一只把 509 种签名降到 508，几乎没用。
  必须配合 screen 等价类、业务通配（BATCH）、登录标签等价这些**基于业务理解的规则**才有效。
- **同骨架参数化盲并**：「更新/確認済/完了登録」三块骨架相同但业务后果不同
  （完了登録终结流程），机器盲并会点错按钮。**结论：参数化合并必须逐族人审。**
  「检索三兄弟」（項目名検索/照会・検索/代理店不備一覧/担当者検索，277 本书受益）
  是第一个安全候选，等页面 HTML 到位后人审执行。

### 成功的关键动作

- **509 个动作签名逐条过目**（不是逐本读，是去重后读动作——等价于读完 450 本的
  全部业务内容）。这个方法可复用：面对"量很大必须逐个读"的场景，先去重。
- **把用户的每一句质疑当数据验证请求**，而不是当批评。三次质疑（150/160 没归上、
  为什么还有未カバー、块太碎）每次都挖出真 bug。
- **所有状态变更走 execution-status.json 的 status3Map 单点**，改完重跑 build
  全链路自动刷新。

## 四、思考方法（怎么想的，为什么这么想）

1. **先质疑约束，再设计方案**。"公司机不能装东西"实际是"没有管理员权限"，
   绿色 node.exe 不需要安装——约束没验证过就不当设计前提。（但注意：在**哪台机器**
   验证也要先问清，不然就是错误 #2。）
2. **去重降维**：450 本 × 24 行 → 442 个原子动作 → 94 个原语。每降一维，
  "全部读一遍"就从不可能变成半小时的事。
3. **书写差异 vs 业务差异的判定准则**：同一个动作的书写变体（引号/押下/初期値/
   dataClass）可以归一；**业务后果不同的（権限エラー≠システムエラー、
   MS≠代理店、完了登録≠更新）永不合并**。拿不准时不并，标给人审。
4. **覆盖率必须配三状态才有意义**：静态匹配（full/partial）说"能拼出来"，
   三状态（planned/coded/verified）说"做到哪了"。两个口径永远分开显示，
   混用就是上次"68% 虚数"事故的根源。
5. **机器只做有确定性规则的事**：归一化规则确定→机器做；参数化合并需要业务
   判断→人审。分界线画在"错了会不会点错按钮"。
6. **每轮改完必须全量回归**：build_blocks 重跑 + verify_routes PASS + 无头浏览器
   渲染检查 + 关键 case（009/150-13-004/160-01-004）抽查。这套组合拳今天
  抓出了假阳性 verified 和去重 bug。
