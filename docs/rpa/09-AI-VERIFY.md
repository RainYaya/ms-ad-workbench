# AI 确认流程 / 参数 / 可行性的工作规程

> 用户明确要求：「流程和参数这两个必须实际开 AI Agent 来确认，不然肯定会出错。」
> 这份文档定义 AI Agent 具体怎么干、产出什么、什么算合格。

## 为什么必须 AI 读，不能只靠程序

程序能做：
- 从 Excel 抽出「标签 → 值」
- 把标签映射成 selector
- 验证"这步能不能执行"

程序**不能**做：
- 判断「各項目に入力」到底要填哪几个字段
- 判断「照会内容チェックボックス」是表内第几行的那个
- 判断「※ 保险种类选择画面で设置」意味着不用填、要走弹窗
- 判断某一行的手顺是不是写错了

**这些必须读原文 + 理解意图。** 所以要 AI Agent，而且必须留证据。

## 三类确认，分开做

### A. 流程确认（每本一次）

**输入**
- 手顺正文（`workflow.rows`，含 `sourceRow`）
- 别紙操作内容 / 表示内容
- `ui-dictionary.json`（有哪些控件）
- `ui-screens.json`（画面名 → 画面码）

**Agent 要产出**：`flows/<CASE>.yaml`

**必须满足**（否则不算完成）：

| # | 要求 | 怎么检查 |
|---|---|---|
| 1 | 每个 step 有 `row` | `rows == 连续覆盖 ` |
| 2 | 手顺每一行都有对应 step，或被显式标为"跳过+原因" | 逐行核对 |
| 3 | 不确定的字段标 `pendingRuntime` 或 `manual`，**不许猜** | 人工抽检 |
| 4 | 期望值放 `expect:`，不混进输入字段 | 编译无假错 |

### B. 参数确认（每本一次）

**输入**：别紙操作内容 + 表示内容

**Agent 要产出**：`values:` 块，每条带 `row` 和 `source`

| source | 含义 | 例子 |
|---|---|---|
| `human` | 人手输入的具体值 | `AHE61` |
| `sys` | 系统生成 | `システム日＋7日`、`現在日付` |
| `blank` | 明确空白 | `（入力なし）`、`空白` |
| `auto` | 自动设定 | `（自動設定）` |
| `na` | 対象外 | `対象外`、`連動しない` |
| `manual` | 手顺没写清，要人现场填 | 别紙写「参照」但没给源 |

**"参数正确"的判定**：

1. 每个值都能指回别紙的某一行
2. `source` 分类正确（把`対象外`当值填进去 = 错）
3. 标 `manual` 的必须列出「为什么需要人填」

### C. 可行性确认（每本一次，轻量）

**Agent 回答三个问题**：

1. **这本能不能自动化？** 分三档
   - `browser` — 纯浏览器操作
   - `mixed` — 浏览器 + 批处理/文件
   - `non-browser` — 纯命令/批处理，不该进自动化

2. **有哪些步骤是模板里看不出来的？**（列出 `pendingRuntime`）

3. **有哪些前置条件会静默失败？**（如 `種目` 未选 → 保险种类按钮无反应）

## Agent 的工作纪律（硬约束）

从 `02-DEV-RULES.md` 和 `07-REQUIREMENTS.md` 继承，此处强调：

1. **不许猜 selector** — 查不到就报 `pendingRuntime`
2. **不许为了通过改断言** — 断言不过先判断是期望值错、selector 错、还是功能真的坏了
3. **必须留行号** — 没行号 = 无法验证 = 不算完成
4. **不确定就标出来** — `manual` / `pendingRuntime` 是合法产出，硬猜不是
5. **先看代码再动手** — 用户原话：「碰到什么情况，也是先看代码了解」

## 用户特别强调的两点

### 1. 「了解清楚了再弄」

> "以前也聊过：了解清楚了再弄。"

**执行方式**：Agent 拿到一本手顺，第一步不是写 yaml，是：
- 读完整手顺
- 读涉及画面的真实 HTML
- 对照别紙
- **然后才写**

今晚的教训：我上来就改代码，在"改-跑-错"循环里空转 1 小时。后来花 5 分钟读 AMA03.html，
一眼就看出 `種目` 是 hidden + select 两个控件。

### 2. 「尽量多看前端引用代码」

> "测试的时候尽量多看发给你的前端引用代码。"

**执行方式**：
- `reference/webapps/` 是权威来源（Shift_JIS）
- 遇到"点了没反应" → 先读 JS，找守卫条件（`if (selectedIndex <= 0) return;`）
- 遇到表内字段 → 先读 `<tbody>` 模板，看行结构

## 产出物检查清单

一本做完，目录里应该有：

```
flows/<CASE>.yaml           流程 + 值（带 row）
（字典/别名如有新增）
logs/<CASE>-flow/run.json   执行结果
```

**合格标准**：

- [ ] `compile_flow` 退出码 0
- [ ] `errors` 为空
- [ ] `pendingRuntime` 每条都有 note 说明为什么
- [ ] `rows` 连续覆盖手顺范围
- [ ] 每个 `values` 有 `row` 和 `source`
- [ ] 手顺里明确跳过的行，在 yaml 里注释了原因

## 批量时的分档

不要 450 本一个模式。先分档：

| 档 | 本数 | 处理方式 |
|---|---|---|
| 纯浏览器·主干 | ~374 | 通用流程，AI 逐本生成 + 抽检 |
| 混合（浏览器+批处理） | ~65 | 拆分：浏览器部分自动化，批处理标 `manual` |
| 纯非浏览器 | ~11 | 不进自动化，标记并跳过 |

**先做「纯浏览器·主干」这一档**，因为它占多数、结构最像、验证最快。

## 汇总要求

每批做完，产出一份汇总：

```markdown
## Batch N (cases X-Y)

| case | steps | errors | pending | 可行档 | 备注 |
|---|---|---|---|---|---|
| AZ-110-01-009 | 44 | 0 | 8 | browser | 表内动态name |
...

### 本批新增的共享配置
- ui-aliases.json: +3 条
- ui-rowfields.json: +1 画面

### 本批发现的新问题
- ...
```

**这个汇总比 450 个 yaml 更重要**——它让人一眼看出"哪里有系统性问题"。
