# 需求与定义（bikuri 原话 + 我的理解）

> 这份文档记录**用户到底要什么**。后面所有设计都要能追溯到这里。
> 写法：先抄原话，再写我的理解，最后写"所以技术上意味着什么"。

---

## 一、根本目标

> "自动化的本质不就是流程正确、参数正确，就可以自动执行下去嘛。"

**理解**：这套东西的正确性只有两个维度。

| 维度 | 定义 | 怎么验证 |
|---|---|---|
| **流程正确** | 该点的点了、该填的填了、顺序对 | 每一步能指回手顺的 Excel 行号 |
| **参数正确** | 填进去的值和别紙写的一致 | 每个值能指回别紙的行，且标出来源类型 |

**技术含义**：
- 每个 step 必须有 `row`（手顺行号）
- 每个 value 必须有 `row` + `source`（human / sys / blank / auto）
- 没有行号 = 无法验证 = 不算正确

---

## 二、为什么不做"完全自动化"，而要做 RPA

> "虽然能实现完全自动化当然最好，但我希望比起完全的自动化，也能有一个我自己可以来定制化的东西。"
> "哪怕我手动，应该也可以形成一个自动化的流。"
> "我自己创造一个自动化的流，实现高度定制化也是可以的。就真的成为了一种别人的那种和 UiPath 或者 RPA 那种工具差不多嘛。"

**理解**：用户要的不是"跑得更多"，是**"我改得动"**。

**技术含义**（这是硬要求，不是可选项）：
1. 流程必须是**人能读、能改**的文本（YAML），不是 16 个 json 文件里的 selector
2. 必须能 `do: manual` —— 停下等人做
3. 必须能"改一个值就重跑"，不用动 450 本
4. 必须能自己新建一个流程（照格式写几行）

---

## 三、真机上的痛（这是重做的直接原因）

> "今天，我去了公司，在真实环境下跑了一下，真的是惨不忍睹啊！"
> "之前的设计是一个流程出错就关闭了，不好 debug。"

**技术含义**：
- **失败绝对不许关闭浏览器**
- 必须能停下来看现场
- 必须能"就地改"（手填一个值继续）
- 必须有截图和当时的 URL

→ 这催生了 `05-EXECUTOR.md` 里的 6 键交互协议。

## 四、已有的资产怎么办

> "我觉得肯定是有参考的。而且他说不定已经做得很好了。"
> "之前的自动化不能浪费，本身也可以成为模板，只是相当于在一个 RPA 软件里面已经预制了模板，我可以随便修改而已。"
> "如果之前做的错误很大，方向性也很大...就可以完全推翻，也没问题。"

**理解**：不要因为"是我做的"就舍不得，也不要因为"要重做"就全扔。

**实际决定**：
- 252 个积木 → **保留**，定位改成"模板片段库"
- `block-selectors*.json` → 被 `ui-dictionary.json` 替代，迁移完归档
- 9 个 params 文件 → 被 `flows/*.yaml` 的 `values:` 替代
- `build_blocks.py` 的 n-gram + DP → **废弃**（它优化覆盖率，不是对不对）
- `runner.mjs` → **不动**，新写 `run-flow.mjs`

## 五、数据是完整的

> "本身就没有原始的那个 xlsx 文件，这个项目的起步，就是我先用 VBA 把原始文件的流程和页纸全部抓取下来，转换成了 JSON 格式。"
> "其实数据应该是全的，就是每一本手顺，我都抓下来了。"

**理解**：数据完备，不需要重新抓。

**核实结果**（我实测过）：
- `v2/data/cases/` 1386 本，450 本全覆盖
- 416 本带【別紙】操作内容
- 34 本无別紙 —— 是登录/异常/批处理，本来就不需要

**所以**：不存在"数据缺失"问题。之前我说"167 本缺原始数据"是**看错了文件**，已更正。

## 六、业务本质

> "其实就是几个页面来回切换、填数值、点按钮这种东西而已。"

**理解完全正确。** 实测数据支持：

- 450 本、10803 行手顺
- 55 个画面名，其中 **8 个是主干**
- 171 种操作项，前 5 种覆盖大部分：
  ```
  1023 次  「検索」押下
   637 次  各項目に入力
   409 次  「OK」押下
   233 次  「No.」リンク押下
   222 次  画面各項目入力
  ```

**主干流程**：
```
申込書品質管理メニュー
  → 不備内容入力（新規）
  → 不備一覧
  → 不備内容入力（更新）
  → [項目名検索 / 募集人検索 / 保険種類選択]  ← 三个弹窗
  → 照会内容編集
  → 訂正内容確認
  → 完了登録
```

450 本 = 这条主干 + 不同的值 + 不同的分支。

## 七、定制化到底要什么（a 和 b）

> "就真的成为了一种别人的那种和 UiPath 或者 RPA 那种工具差不多嘛。"

我确认过，用户要的是两件事（不是二选一）：

**(a) 改一处就生效**
- 某个值变了 → 改一行
- 某个 selector 变了 → 改字典一处，450 本全生效

**(b) 能自己造新流程**
- 出现手顺没写过的新流程，自己拼几步就能跑

**技术含义**：两者共用同一个底座。

```
         ┌── (a) → ui-dictionary.json + ui-aliases.json
底座 ────┤
         └── (b) → flows/*.yaml 的格式 + 一个可视化编辑器
```

不需要做两套系统。b 比 a 多的，只是**编辑器 UI**。

## 八、AI 的角色

> "对于所有的手顺内容，其实某种程度上来说，你是 AI，很厉害，应该是能够理解意图的。"
> "我觉得必须要 AI 实际读懂那个'手串'之后，才能来决定流程。"

**理解**：AI 负责"读懂手顺 → 产出流程"，但**产出必须可验证**。

**我的补充（用户同意）**：AI 读完不能只给一个"OK"，要留下证据链：

```yaml
values:
  部店課支社コード: {value: "AHE61", source: human, row: 13, note: 変更となる可能性あり}
```

这样人一看就知道：这个值来自别紙第 13 行，备注说"可能变"，需要现场确认。

## 九、对 AI 的硬性约束（最重要的部分）

这些是用户反复强调、或从失败中总结出来的：

| # | 约束 | 来源 |
|---|---|---|
| 1 | **不许猜 selector** | `選択欄` 被猜成 `選択` 按钮，现场会点错 |
| 2 | **宁可报错** | 用户原话："明明只有一点点错误，自己稍微修改一下就完了的事情" —— 报错才能改，猜错查不出来 |
| 3 | **必须留行号** | 否则"不知道该怎么弄" |
| 4 | **失败不退出** | 真机痛点 |
| 5 | **手工配置与生成物分开** | 生成器覆盖过一次，白干 |
| 6 | **大文件不用 heredoc 写** | 今天截断过 5 次以上 |
| 7 | **改代码前先验证单点** | 在"改-跑-错-改"循环里空转了 1 小时 |

## 十、验收标准（用户视角）

一本手顺算"做完"，必须同时满足：

1. **流程对**：每个 step 能指回手顺行号，且人能读懂
2. **参数对**：每个值能指回别紙行，来源类型标注清楚
3. **跑得通**：mock 上 done = 总步数
4. **改得动**：人能只改一个值就重跑，不用碰别的东西
5. **查得出**：失败时知道是哪一行、哪个字段、什么原因

**只有 1+2 是"正确"，3 是"能执行"，4+5 是"能维护"。用户要的是全部。**

## 十二、A / B 两条路（2026-10-26 夜确认）

用户：「刚刚我们聊了 AB 两条路，可以定制化，也可以修改参数。」

| | A 路 | B 路 |
|---|---|---|
| 名字 | 改一处就生效 | 自己造新流程 |
| 用户要什么 | 值变了改一行；selector 变了改一处，450 本全生效 | 出现手顺没写过的新流程，自己拼几步能跑 |
| 技术实现 | `ui-dictionary.json` + `ui-aliases.json` | `flows/*.yaml` 格式 + 可视化编辑器 |
| 工作量 | 小（数据层） | 中（多一个编辑器 UI） |
| 共用底座 | ✅ 完全共用 | ✅ 完全共用 |

**不是二选一，是同一个底座的两个出口。**

底座 = 动作层(10个) + 字典层(ui-*.json) + 流程格式(flows/*.yaml) + 执行器(run-flow.mjs)。

B 比 A 多出来的只有编辑器 UI——而 `v2/lego.html` 已经有底子了，
把它的导出格式改成 flow YAML 就是 B 的成品，不用重写。

## 十六、R0：碰到问题先查代码（2026-10-26 23:34 确认）

> 用户：「那也就是说，其实碰到问题，就查 reference 这也算一条必须记住的对吧。」

**是的，而且这是优先级最高的一条。**

### 为什么它最高

因为它能防止今晚发生过的所有低效：

| 今晚的错误 | 如果先查代码 |
|---|---|
| 改-跑-错 空转 1 小时 | 读 `AMA03.html` 30 秒看出种目有 hidden+select 两个控件 |
| `\b` 写成退格符（`\x08`） | 看正则 pattern 的实际字符就能发现 |
| heredoc 截断 10+ 次 | 文档 P14 早就记着，该换 Write 工具 |
| 字典抓错控件 | `grep '<input'` 一眼看出两个控件 |

### 具体规则

**改任何代码之前，必须能回答两个问题：**

1. 现在的实际结构是什么？（引用具体文件 + 行号）
2. 为什么现在会失败？（引用具体代码）

**回答不出来 = 不许动手。**

### 权威顺序（不许搞反）

```
reference/webapps/        真机前端源码（Shift_JIS）   ★ 最高
automation/node-runner/mock-src/   拿去跑的 mock     基于前者，可能被改
v2/mock-src/              Pages 演示副本            别拿来判断
v2/data/cases/*.js        手顺 / 别紙数据            ★ 数据源
```

### 五种症状的查法

见 `10-DEBUG-BY-CODE.md`，摘要：

| 症状 | 先查什么 |
|---|---|
| 点了没反应不报错 | 按钮的 `onclick` 函数，找守卫条件 |
| 元素找不到 | `grep '<input'` 看有几个同名控件 |
| 字段名对不上 | `grep 'field_title'` 对比别紙说法 |
| 表内字段定位不了 | `<tbody>` 模板；空的 → JS 动态插入 |
| 跑完但结果不对 | 手顺原文（不是别紙摘要） |

### 一句话

> **问题不在"猜错了"，在"允许自己猜"。**
