# 可行性分析：每本到底要定制多少

> 用户的疑问：「如果每一本都需要专门定制很多复杂的东西，那就算了。」
> 这份文档用**实测数据**回答：不需要。

## 结论先说

**不需要每本定制。** 全量实测：

| 指标 | 数值 |
|---|---|
| 别紙不同标签 | 91 种 |
| 已被字典覆盖的行 | 1906 / 2203 = **86%** |
| 未覆盖 | 297 行 = 14% |
| 其中「非浏览器」（命令/批处理/服务器） | 21 行 |
| **真正需要在画面上补的** | **276 行 = 全体的 12%** |

而这 86% 的覆盖率，是靠**极少的共享配置**达成的：

```
ui-aliases.json    19 条别名
ui-rowfields.json   5 个画面的行内字段
```

**19 + 5 = 24 条配置，覆盖了 86% 的行。** 这就是"不需要每本定制"的证据。

## 为什么能这样

因为本质就是用户说的那句话：

> "本质就是那几个动作在重复，比如点按钮、输参数，或者做跳转之类的。"

实测支持：

- 1613 个执行步骤 → 只有 10 种动作
- 55 个画面名 → 8 个是主干
- 171 种操作项 → 前 5 种覆盖大部分

**差异只在「值」和「走哪条分支」，不在「动作」。**

## 剩下 12% 是什么

按性质分四类，没有一类需要"逐本定制"：

### 1. 同义写法（加一条别名即可）
```
具体的内容 / 具体的説明 / その他の項目   ← 共通の自由記述欄
代理店への募集状況の確認要否 / 保険始期日と届出日の関係  ← チェック項目
証券送付区分 / 変更確認書送付 / 変更確認書課支社送付の理由
役職段階コード / 大種目コード / 保種コード
```
→ 每加一条 `ui-aliases.json`，所有用到那个说法的本一起生效。

### 2. 非浏览器（本来就不该进自动化）
```
実行コマンド(27) / java -jar / chmod / cp -p / echo / DBサーバ / 戻り値
```
→ 这类要**识别出来并排除**，不是"补进字典"。

### 3. 只显示字段（只能断言，不能填）
```
作成日時 / 異例管理番号 / 申込日 / 届出日 / 取消・変更の計上日
```
→ 字典里 `kind: text-only`，流程里只能出现在 `expect:`。

### 4. 特定业务的专有字段（少数本）
```
取消保険料(10) / 再計上証券番号 / 変更事由1-6
```
→ 属于「取消計上」「異例」这些特殊业务线，加起来十几本。

## 实测：009 到底改了多少

用户观察到「你跑 09 的时候改了很多东西」。**确实改了 5 处，但全在共享层，不在 009 本身。**

| 改了什么 | 在哪 | 影响范围 |
|---|---|---|
| 字典优先选非 hidden 控件 | `build_ui_dictionary.py` | **全部 53 画面** |
| 用控件自己的 type 判断 | 同上 | 全部 |
| 按钮区分 id / name | 同上 | 全部 |
| `{变量}` 编译期插值 | `flow-loader.mjs` | 全部流程 |
| 跨页面查找 + 重试 | `run-flow.mjs` | 全部流程 |

**009 的流程文件本身，从写出来到现在只改过一次**（加 `requires` 和 `popup` 标记）。

这正是要的形状：**改的是地基，不是每本**。

## 风险在哪（诚实说）

| 风险 | 程度 | 应对 |
|---|---|---|
| 表内动态 name（`list[n].xxx`） | 中 | 已标 `pendingRuntime`，真机 DOM 一次确定 |
| JS 动态插入的结果区（`<div id=Result>`） | 中 | 同上 |
| 画面名表记ゆれ（`異例取扱管理`） | 低 | 真机看一眼标题即可 |
| 特殊业务线（取消計上/異例） | 低 | 十几本，单独处理 |
| **未知的未知** | **?** | 只能靠真机跑出来 |

最后一条是唯一无法用数据消除的。所以路线是：**先真机跑 1 本 → 再跑 4 本 → 再批量**，
而不是一次性 450 本。
