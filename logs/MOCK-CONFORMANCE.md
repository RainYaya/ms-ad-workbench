# 模拟环境符合性评估

> 结论先说：**UI 流程形状基本符合；业务语义、主档数据、后端副作用不符合。**
> 现在的 446/450 只能证明“block 能在 mock 上走完”，不能证明“mock 符合式样书”。

## 1. 规模对照

| 项目 | 数量 |
|---|---:|
| 结合测试本 | 450 |
| 场景 | 347 |
| 手顺 flow 行 | 3322 |
| 手顺 check 行 | 1412 |
| mock HTML | 65 |
| 式样书中的不同“画面”名 | 42 |
| block | 252 |
| block steps | 1608 |
| 唯一 selector | 206 |
| 唯一字段 | 164 |
| mock 表单字段 | 2504 |

画面形状覆盖不低：42 个画面名对应 65 个 HTML（含变体）。  
但这只是“有页面”，不等于“页面行为正确”。

## 2. 当前通过率

```text
446 / 450 mock flow pass
4 / 450 fail
```

4 本失败不是环境崩溃，而是别纸值与 mock 校验规则冲突：

```text
AZ-110-01-011
AZ-110-01-012
AZ-310-01-011
AZ-310-01-012
```

这 4 本反而说明：mock 里确实写进了一些业务规则，但规则是否来自式样书，没有独立验证。

## 3. 行为保真度

| 维度 | 评估 | 证据 |
|---|---|---|
| 画面存在 | 较高 | 65 HTML / 42 画面名 |
| 画面迁移 | 较高 | 446/450 flow，213 goto，65 popup |
| 点击/输入 | 较高 | 441 click，256 fill，13 select |
| 业务校验 | **低** | 只有 7 个画面有 `formValidate`；大量 check 行没有对应规则 |
| 主档数据 | **低** | 62 组硬编码数组；部分选项是为让测试通过后加的 |
| 后端副作用 | **无** | batch / APログ / DB / メール / 外部系统全部人工或代理 |
| 证据真实性 | 中 | 2972/3034 画面HC exact，但 149 个 block 含代理断言 |

## 4. 最关键的失真点

### 4.1 纯代理 block

```text
23 个 block 没有任何真浏览器动作
98 本至少用了 1 个纯代理 block
6 本全部 block 都是纯代理
```

这 6 本即使显示 pass，也没有实际浏览器验证：

```text
AZ-150-05-001
AZ-150-07-001
AZ-150-08-001
AZ-150-10-004
AZ-200-07-005
AZ-200-07-006
```

它们主要靠“某个菜单/表单可见”来代替 batch / APログ / テーブル确认。

### 4.2 mock 代替断言

```text
245 本 / 415 steps 是 mock 代替
```

这些不是人工，但也不是 mock 验证通过；只是 mock 里没有后端/弹窗/消息。  
真机加 `--live` 才会真正执行 assert。

### 4.3 主档是为了测试补的

例：为了让 31 本保险种类用例通过，`AMA03` 里加入了：

```text
11A0 クルマの保険／はじめての自動車保険
13A0 クルマの保険・一般用
03A0 1DAY保険／GK クルマの保険・ドライバー保険
```

这证明 mock 主档不是从式样书主档生成的，而是按测试参数补的。  
这类“补到能过”的修改，不能作为符合性证据。

### 4.4 参数仍有未落实

```text
1424 个对照项
1265 一致
151 规则/自動
8 手顺内多值
56 本 auto-only
40 本 auto-only 但 block 实际引用业务参数
```

mock 对这些参数大多只做“填进去”，不做主档校验。

## 5. 结论

### 可以认为符合的部分

- 菜单 → 画面 → 输入 → 确认 → 完了 的**点击路径**
- 画面截图与 URL 迁移的**证据采集**
- 一部分输入校验（如 `AMA03` 的種目/入力区分规则）
- 450 本的 block 组合顺序

### 不能认为符合的部分

- 业务规则完整性：大量 check 行没有对应 mock 规则
- 主档数据：按测试补，不是按式样书生成
- 后端副作用：batch / APログ / DB / メール / 外部系统没有真实模拟
- 代理断言：149 个 block 里有代替断言
- 纯代理本：6 本没有任何真浏览器验证
- 参数：56 本仍依赖 auto，40 本 block 实际引用业务参数

## 6. 应该怎么重建

不是重写 450 本，而是重建**画面模型**。

### Phase 1：从式样书抽模型

对 42 个画面 / 3322 个 flow 行 / 1412 个 check 行抽取：

```text
画面
  字段（name / label / type / required / options）
  按钮（code / 条件 / 迁移先）
  校验（条件 / 消息 / 允许值）
  初始值 / 主档
迁移
  从画面 + 操作 + 条件 → 到画面
```

每条规则保留出处：`caseId / sheet / row / cell`。

### Phase 2：和现有 mock 做 diff

输出三类差异：

```text
mock 有、式样书没有  → 可能是为测试补的
式样书有、mock 没有  → 缺失行为
两边都有但规则不同    → 规则冲突
```

### Phase 3：按画面重建，不按本重建

42 个画面远比 450 本小。  
先重建差异最大的画面；block 只作为回归测试，不作为实现来源。

### Phase 4：重新跑 450

验收标准不是“全绿”，而是：

```text
纯代理 block = 0
mock 代替 step 有明确真机断言
每个 check 行有 mock 规则或人工标记
主档值能追溯到式样书
```

## 7. 一句话

**当前 mock 是一个“能点的测试夹具”，不是“按式样书复原的系统”。**  
它适合产出 UI 流程和截图证据，不适合证明业务正确性。  
要符合，必须从式样书生成画面/字段/迁移/校验/主档模型，再用 450 本做回归，而不是继续按失败本补 mock。
