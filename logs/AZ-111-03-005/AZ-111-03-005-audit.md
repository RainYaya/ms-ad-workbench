# AUDIT — AZ-111-03-005（排他エラー確認：完了取消ボタン / 不備登録 / STANDARD）

## intent
完了登録済みの不備データ（AZ11103/0000000005、完了日入力済・営業/代理店対応状況=完了・営業連携済）を
営業ユーザが開き、他端末（事務S）更新後に「完了取消」を押すと排他エラー MAZG101W050 が出ることを確認する。
表示内容1（完了済データの初期表示）、表示内容2（他端末更新後）、表示内容3（エラーメッセージ）の3段階確認。

## 参数核对（不一致のみ詳細）
- policyNo=AZ11103 / detailNo=0000000005（generated.json）→ 別紙と一致、`val="params.policyNo"` で実接線。
- completeErrorCode=MAZG101W047（auto.json）vs 別紙期待 MAZG101W050 — 不一致だが未接線（004 と同型）。
- 事前準備の「完了登録済データ」（完了日入力・対応状況=完了・営業連携済）を作る積木が本Caseに無い。
- 004 との差分は detailNo（0000000004→5）と最終ボタン（完了登録→完了取消）のみで、パラメータ構造は同一。
  「パラメータ差分＝別紙差分」の観点では整合（依頼区分 照会/連絡 の差は別紙にあるが積木未使用項目）。

## doubts[]
1. MAZG101W050 断言不在＋completeErrorCode param 不一致（W047）— 004 と共通の系統課題。
2. **事前準備の「完了登録済」状態を本Case内で作れない**（完了登録→完了取消の連結Caseも無い）。
   真機では事前準備Caseの実行順序依存になる可能性。実行順の前提を bikuri が持つべき。
3. 依頼区分=照会（005）vs 連絡（004）の別紙差分が、どちらもテンプレ既定「連絡」表示で潰れている。
   データ差分を画面で区別できない mock の構造限界。
4. 検索結果 assert の検出力ゼロ問題（テンプレ静的行、004 と同じ）。
