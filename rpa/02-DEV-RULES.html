★★★ R0（最高优先）：碰到问题先查代码，不许猜

用户 2026-10-26 明确要求。详见 10-DEBUG-BY-CODE.md。

改任何代码之前，必须能回答：

  1. 现在的实际结构是什么？（引用具体文件 + 行号）
  2. 为什么现在会失败？（引用具体代码）

回答不出来 = 不许动手。

权威顺序：reference/webapps/（真机源码，Shift_JIS）> mock-src > v2/mock-src。

一、绝对不许做的

R1. 不许猜 selector

字典里查不到就报错并给出行号，不要用模糊匹配糊过去。

# ✅
if not hit: errors.append(f"row {row}: label not in {screen_key}: {label!r}")

# ❌ 绝不允许
hit = hit or guess_by_similarity(label)

理由：選択欄 被猜成 選択 按钮；.... 被猜成错的那个。用户现场会看到"点了没反应"或"点错按钮"，比报错难查 10 倍。

R2. 不许把"仅显示字段"当输入字段

字典里 id: null 的字段是后端填的只读值，只能断言，不能填。

现状：106 个有 id（可输入）/ 131 个无 id（只显示）

如果混用会怎样：#field_agent_name 这种字段 fill 进去无效，但它会静默成功（Playwright 允许改 readonly 的 value），然后断言又能过 —— 假阳性。

R3. 不许在流程文件里写 CSS

# ✅
- do: click
  新規登録: ""

# ❌
- do: click
  selector: "#act001to100"

理由：CSS 一进流程文件，450 本就要各改一遍。

例外：确实需要精确 selector 时，写进 ui-dictionary.json，流程文件只引用标签。

R4. 不许"为了通过"改断言

如果断言不过，先判断是：

  1. 期望值错（手顺抄错）→ 改 values
  2. selector 错 → 改字典
  3. 功能真的坏了 → 报告，不要改断言

红线：execution-status.json 不能手改（历史教训）。

二、必须做的

R5. 每一步必须带 Excel 行号

- row: 24

用途：

  • 出问题时能指回原文
  • 改的时候知道在改什么
  • 450 本迁移时能验证"44 行手顺 → 44 步"是否一一对应

验证方法：rows == list(range(14, 58))（009 已通过）

R6. 期望值和输入值分开

# ✅ 输入
- do: fill
  部店課支社コード: "{部店課支社コード}"

# ✅ 期望
- do: expect
  expect:
    遷移: 表示内容１

理由：混在一起会让编译器把 遷移 当成字段查字典，报 17 个假错误（这是实际发生的）。

R7. 运行期才能确定的，明确标记

{ "label": "検索", "how": "runtime-resolve", "status": "unresolved",
  "note": "JS 拼接 name，需真机 DOM" }

然后 compile_flow.py 输出 pendingRuntime 清单。

理由：6 个这样的字段比 6 个错误猜测好。至少知道缺什么。

R8. 脚本必须能在两种环境跑

build_ui_dictionary.py 的 --src 参数：

# mock / 仓库内的模板
python tools/build_ui_dictionary.py

# 真机抓下来的页面
python tools/build_ui_dictionary.py --src capture-1027/pages --merge

理由：真机发现差异时，要能一键用真机数据覆盖字典，而不是手工改 json。

R9. 中文/日文输出必须处理编码

import sys
sys.stdout.reconfigure(encoding='utf-8')

Windows 控制台 GBK 会让日文直接崩。

三、验证标准

每个产出物必须能通过下面这些检查才算完成。

字典

  • [ ] screens 数量 ≥ 50
  • [ ] 有 id 的字段 ≥ 100
  • [ ] 别紙标签覆盖率 ≥ 70%（当前 73.5%）
  • [ ] 无空 label / 无乱码 label

流程文件

  • [ ] compile_flow.py 退出码 0
  • [ ] errors 为空
  • [ ] rows 连续覆盖手顺范围
  • [ ] pendingRuntime 每条都有 note 说明为什么

抓取工具

  • [ ] mock 上能跑（已验证：菜单→新規→弹窗 4 阶段全抓到）
  • [ ] 同一画面不重复保存（已验证：dedupe 1200ms）
  • [ ] 文件名不带 .html.html（已验证）

四、用户的明确要求

原话记录：

"比起完全的自动化，也能有一个我自己可以来定制化的东西" "哪怕我手动，应该也可以形成一个自动化的流" "希望加入这个功能（手动输入）" "主要是该怎么实现这个东西，我不太清楚"

所以：

  • 手动介入不是降级方案，是一等公民
  • 流程文件必须人手可写
  • 要有 do: manual 让执行器停下等人

五、错误处理原则

现场 vs 开发

场景行为
开发/mock报错，退出码非 0
真机现场不许退出。停下来，等人决定

现场交互（待实现，见 03-ROADMAP）：

[Enter] 重试   [s] 跳过   [v] 手填值   [e] 编辑这步   [q] 退出

理由：今天真机最大的痛点就是"出错就关浏览器，什么都看不到"。
